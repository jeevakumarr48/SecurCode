## Supported deployment modes

Non-demo development and private production API resources require database-backed bearer sessions. The first administrator is created through the one-time bootstrap route gated by `SECURCODE_BOOTSTRAP_TOKEN`; generate it with a cryptographically secure random generator, deliver it through a deployment secret manager, and remove it from the runtime environment immediately after setup. Private production startup requires the token only while the configured database has no accounts; existing-account restarts do not require it. Passwords are scrypt-hashed; opaque session tokens are random, stored only as SHA-256 digests, and expire after eight hours. Password changes and account disabling revoke sessions. The public production demo deliberately permits only read APIs and its sample scan route. Production requires exact HTTPS origins. FastAPI Swagger, ReDoc, and OpenAPI routes are disabled in production. Bind local development to loopback.

The Windows-only local helper `scripts/bootstrap-admin.ps1` resolves the effective database path using the backend's default and relative-path rules. It refuses to create a database, requires an existing `auth_users` table and zero total accounts, and supports `-WhatIf` for a read-only check. During actual setup it starts a temporary loopback-only API with a newly generated transient bootstrap token, prompts for the chosen credentials privately, verifies bootstrap and login, confirms both temporary sessions are revoked, then stops the helper API. Its read-only dry-run was verified against the current local database; account creation was not performed. The helper is not a hosted-production bootstrap mechanism.

Roles are administrator, security analyst, developer, and read-only. Project creators become members; administrators can grant membership using `POST /projects/{project_id}/members`. Non-administrators are restricted to member projects for project, scan, finding, external scanner, and SARIF import routes. Global dashboard, history, statistics, finding search, audit, incident, notification, and report routes are administrator-only until those data sets have complete project scoping. Membership removal and ownership transfer are not implemented. Authentication is not equivalent to deployment-grade multi-tenant isolation; validate the route policy before exposing private repositories.

API responses include `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and a restrictive Content Security Policy (except the interactive API documentation routes). This is not a complete deployment header policy: configure HTTPS redirect and HSTS at the HTTPS termination layer and set an appropriate policy for the separately hosted frontend. Private production requires exact HTTPS CORS origins, an absolute SQLite path, and an existing database-parent directory; these checks do not prove that the configured path is a durable mount. Login throttling and the built-in scan semaphore are process-local. Keep the authenticated API at one process and one replica; do not autoscale or use overlapping workers until shared rate limiting and appropriate shared storage are available. The browser holds bearer tokens in memory, not cookies; CORS does not allow credentials. MFA, account recovery, and external secret rotation are not implemented.

## Filesystem and scanner boundary

Scans are static and do not execute source code. API paths reject absolute paths, traversal, and symbolic-link components. Discovery excludes dependency, generated, cache, and build directories. Configurable file-count, directory-depth, per-file byte, and cumulative byte limits constrain scan work. Limits are checked between files; the current implementation cannot interrupt a parser already working on one file. Python syntax failures and unreadable, oversized, or depth-limited sources are reported as incomplete scans, not clean results.

The JavaScript/TypeScript engine is a conservative lexical matcher, not a semantic parser. Findings are leads for engineering review, not proof of exploitability. Location-based finding fingerprints change when a finding moves to a different line. CWE and CVE identifiers are not fabricated.

## Storage and audit

SQLite is the only supported application database and can be relocated with `SECURCODE_DATABASE_PATH`. Schema updates are additive and versions 1 through 7 are recorded; migrations run during application initialization. No automatic backup or retention deletion runs. A hosted deployment must mount durable storage at the configured database path; ephemeral filesystems lose data on restart or redeploy. Create a consistent backup with Python's `sqlite3.Connection.backup()` API while the service is running, or stop the service and copy the database file. Store backups encrypted and separately from the service host; periodically restore a copy into an isolated location and verify it with `PRAGMA integrity_check` before relying on recovery. To restore, stop the service, preserve the current database as a separate incident artifact, place the verified backup at the configured path with restrictive file permissions, then start the service and check `/healthz`. See [deployment and recovery](DEPLOYMENT.md); restore and rollback are operator procedures, not application features.

API audit events cannot be updated or removed through application routes. Schema version 2 links events with SHA-256 hashes and exposes `/audit/integrity` for verification. Sensitive metadata fields are redacted before storage and serialization; startup migration 6 redacts legacy audit metadata and rebuilds the chain. The chain detects partial edits and corruption, but it is unkeyed and an operator who can rewrite SQLite can recompute it; remote immutable audit storage remains unsupported.

Secrets and raw source lines are not included in audit metadata or API finding evidence. Finding paths are workspace-relative or redacted. Keep access to SQLite files, process logs, and deployment configuration restricted to trusted operators.

## Public demo controls

The demo validates exact HTTPS frontend origins, only scans the committed demo tree, uses a SQLite transaction to serialize cooldown checks across workers sharing the same database, filters history, reports, and notifications to demo project paths, and rejects write operations. Demo notifications include only scan and critical-finding events tied to scans in that tree. Hosts using separate per-instance SQLite files do not share this rate limit; use a single shared database or an upstream durable limiter before scaling out.

## Release validation limitations

The browser acceptance test runs against a disposable SQLite database and uses credentials generated in memory for that run. It validates local project registration, local scan, findings, and CSV retrieval. The UI explicitly states that repository URLs are metadata only; GitHub repositories are not cloned or scanned by this workflow. GitHub authentication and live repository artifact retrieval are not implemented. Confirm durable storage, TLS/HSTS, frontend headers, and the single-process/replica restriction before private production deployment.
